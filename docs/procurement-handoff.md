# Снабжение: передача клиентской части

Дата: 2 ноября 2026. Контракт: `procurement.v1`.

## Репозиторий и запуск

- Действующий клиент: `C:/1true/A1_client`, ветка `master`. Перед публикацией изменения перенесены поверх `59ae46e`, включая исправления авторизации и серверной подписи из origin/master. Коммит раздела: `feat(supply): add procurement catalog and request workflow`.
- Навигация: **OPS → Снабжение**. Прямая ссылка: `/#/ops/supply`.
- Восстановление: `/#/ops/supply?company=<company_id>&mode=mock|live&job=<job_id>`; идентификатор в URL не даёт права доступа.
- Установка: `npm ci`. Локальный запуск: `npm run dev -- --host 127.0.0.1`.
- Проверки: `npm run test:procurement`, `npm run check:procurement-encoding`, `npm run build:procurement-check`.
- Полный UI-прогон: при работающем локальном Vite на `127.0.0.1:5173` выполнить `npm run test:procurement:ui`. Используется Playwright CLI через npx, отдельная тестовая browser-сессия и синтетические компании; рабочая авторизация не затрагивается.
- Последняя команда выполняет обычные `tsc -b` и `vite build`, принудительно обнуляя старые публичные параметры вебхука при проверочной сборке. Не использовать проверочный `dist` как готовое подключение production.

## Реализовано

Каталог с серверным интерфейсом поиска/фильтров/пагинации, динамические facets, карточка с источниками и противоречиями, добавление в заявку, ручные строки, разбор текста, имитация файловой загрузки, обязательная проверка распознавания, анализ, этапы обработки, промежуточный и окончательный результат, альтернативы и интернет-источники, история, экспорт CSV и XLSX.

В демонстрации постоянно виден баннер «Демонстрационные данные — бэкенд не подключён». Тестовый набор независим от реальных прайсов; реальные 12 358 карточек не загружаются в браузер. Точное совпадение, аналог, уточнение и отсутствие товара представлены отдельными исходами. Нулевой остаток и нулевое число АКБ не смешиваются с неизвестным значением. Количество и единица после неполного распознавания требуют ввода. Цена не доказывает совместимость; UI отображает решение транспорта.

Ручной демонстрационный ввод: одна строка на позицию, `описание;количество;единица`. Кнопка тестового примера подставляет четыре статуса. Тестовые запросы: `000125`, `AC-AG1252`, `УШМ 125 мм`, `DEMO-NOPRICE`, `DEMO-CONFLICT`, `000083`. Ошибки поиска: `DEMO-401`, `DEMO-403`, `DEMO-503`. Название заявки `DEMO-FAIL` создаёт failed job.

## Фактическая граница сервера

В этом репозитории фронтенд Vite и nginx; отдельный шлюз `procurement.v1` ещё не подключён. Включённые перед публикацией изменения origin/master переводят существующий `src/api/n8n.ts` на same-origin `/api` с серверной подписью и убирают HMAC-секрет из браузера. Новый модуль снабжения не вызывает старый procurement workflow; проверку нового шлюза и его области доступа должна завершить серверная сессия.

Live-адаптер подготовлен для:

- `POST /api/a1/procurement/command` — JSON envelope.
- `POST /api/a1/procurement/files` — multipart `file`, `company_id`.
- `Authorization: Bearer <существующий пользовательский session token>` из `getSession()`; `credentials: same-origin`. Токен не включается в payload, fixtures и логи.
- `Idempotency-Key: <request_id>` для трёх запускающих операций.

Маршруты **зарезервированы в клиентском адаптере, но серверные обработчики не развёрнуты**. По умолчанию live возвращает `BACKEND_NOT_CONNECTED` до любого fetch. Публичный несекретный build-флаг `VITE_PROCUREMENT_GATEWAY_READY=true` включает запросы только после внедрения проверенного шлюза. Сейчас флаг не включён. Существующий Vite proxy `/api → localhost:5678/webhook` не является этим шлюзом; не включать флаг поверх него. При подключении серверная сессия должна явно перехватить эти пути до старого proxy/SPA fallback.

Серверная сессия должна валидировать пользовательский токен, установить доверенную личность, проверить членство в `company_id`, затем вызвать А1 с доверенной серверной идентичностью и ограниченной областью доступа. `user_id` из браузера не используется как доказательство личности. Проверка членства должна повторяться для upload, каждого job/result/history/export/download. `company_id` берётся из существующего AuthContext, без жёсткой привязки компании «Инструменты».

Серверная переменная будущего шлюза: `A1_PROCUREMENT_WEBHOOK_URL`. URL и схема серверной аутентификации ещё не предоставлены. Секреты сервера — только age/SOPS по правилам проекта; никаких `VITE_*` для ключей и никаких plaintext-файлов на сервере. Новые ключи, секреты и инфраструктура этой работой не создавались. Миграций, импорта и изменений БД не было.

## Операции и уточнения контракта

Полные примеры см. `procurement-contract-examples.json`; источник истины — `contract.ts`.

| Action | Payload | Result |
| --- | --- | --- |
| catalog.facets | query, filters | kind, categories, brands, sources, attributes, capabilities |
| catalog.search | query, filters, sort, page | kind, items, page, interpreted_query, warnings |
| catalog.get | product_id | kind, product, offers, attributes, source_refs, issues |
| request.parse | text XOR file_ids, title? | job.accepted, job_type=parse |
| analysis.start | draft_id?, revision, title, lines, options | job.accepted, job_type=analysis |
| job.get | job_id | job.status; parsed_request / analysis_id / download по типу |
| analysis.result | analysis_id, page, status_filter? | kind, analysis_id, summary, rows, page, complete, result_revision |
| analysis.history | page | kind, items, page |
| analysis.export | analysis_id, format, result_revision | job.accepted, job_type=export |

Конкретизация полей, которые были описаны в исходном задании без окончательного JSON:

- Категории: `categories: [{path: [{id,label}, …]}]`, сохраняют пути дерева; источники: `sources: [{id,label}]`; бренды: строки.
- `filters.stock_known: boolean|null`: наличие сведений, включая явно указанный ноль, не обещание текущего наличия.
- `capabilities.upload: {enabled, extensions, max_size_bytes, max_files}`; `unavailable_reasons` — словарь сообщений по имени функции.
- `catalog.get.product` содержит ProductSummary; все предложения вынесены в `offers`.
- `analysis.history.items[]`: `job_id`, `analysis_id?`, `title`, `created_at`, `status`, `summary|null`.
- Формат команды с `stock_known`, перечисленными containers facets/history/get и доступными типами характеристик нужно принять в серверной сессии. Это клиентская конкретизация предлагаемого контракта, а не свидетельство согласования с уже работающим backend.

Файлы в mock: `.xlsx`, `.xls`, `.csv`, один файл за раз, до 5 МБ. Загрузка **имитируется**, содержимое не считывается и не передаётся наружу; UI это поясняет до выбора файла и после разбора. Возвращаются четыре тестовые строки с именем выбранного файла в source_ref. Live получает расширения/размер/количество из capabilities; до их получения загрузка отключена. Серверу нужны собственная проверка формата/размера, защищённое хранение и company/user-scoped file_id, ответ HTTP 201 по примеру.

## Повторы, восстановление и опрос

- Новая команда получает UUID. Повтор неподтверждённой команды с тем же телом сохраняет UUID; синхронная блокировка защищает от двойного нажатия. Mock проверяет ключ+тело, при конфликте возвращает `IDEMPOTENCY_CONFLICT`.
- Сервер должен хранить идемпотентность минимум 24 часа; браузер не заменяет эту гарантию.
- Черновик и неподтверждённая команда сохраняются в sessionStorage с ключом пользователя, компании, режима и версии. Секреты туда новым модулем не записываются. Демо-история также в sessionStorage; после закрытия сессии браузера постоянной истории не обещается. Live-история должна храниться на сервере.
- После успешного анализа следующая отправка имеет новую revision; предыдущий job/result остаётся в истории. Перезагрузка распознанной заявки не дублирует строки.
- Активный job восстанавливается по hash и заново запрашивается адаптером. Смена компании/режима перемонтирует рабочую область и отменяет браузерные запросы. Смена раздела не отменяет серверное задание.
- Один последовательный цикл polling, интервал по `poll_after_ms` в пределах 2–10 секунд. Скрытая вкладка приостанавливает запросы; возвращение обновляет статус. До трёх сетевых повторов с увеличением задержки до 30 секунд, затем ручное восстановление. `Retry-After` ограничивает и автоматический, и ручной повтор live-запросов. Серверное задание не перезапускается при сетевом сбое.
- `completed` и `failed` останавливают polling. HTTP 200 с `ok:false` и `job.status=failed` обрабатываются отдельно. Неправильный JSON, версия, request_id или структура не превращаются в пустую выдачу.
- Результат выводится постранично; изменение result_revision сбрасывает курсор. Статусный фильтр не пересчитывает summary по текущей странице. Итоги приходят от адаптера.
- Экспорт доступен только для complete-результата, создаёт отдельный job. Live ожидает защищённую http(s) download-ссылку с expires_at. Mock возвращает временный blob и реальный CSV/XLSX из тестового результата. CSV защищён от начала формул, XLSX содержит только literal string cells. Live-экспорт и защита CSV/Excel должны выполняться сервером.

## Проверено

- `npm run build:procurement-check`: TypeScript и production-сборка действующего клиента. Архивный `a1-dev-ops/apps/web` не запускался и не менялся.
- `npm run test:procurement`: 15/15, включая точный артикул/нули, фильтры и пагинацию, смешанную заявку, отсутствие цены, missing name, partial summary, идемпотентность, версии, 200+ok:false, failed job, изоляцию пользователя/компании, восстановление, upload 413/415, Retry-After, отмену и безопасный экспорт.
- Playwright: поиск `000125`, карточка и Escape, ручная валидация, четыре строки, двойной submit → один job, фильтр результата, reload, CSV/XLSX download, смена компании, 401/503, live без fallback, мобильный viewport 390px без горизонтального переполнения страницы.
- Дополнительный UI-сценарий: неподдерживаемый файл, имитация CSV, восстановление черновика без дубликатов, failed job, смена компании во время анализа.
- Browser harness: запоздалый ответ не перезаписывает свежий; старый запрос и запрос при unmount прерываются.
- Динамические фильтры: серверные операторы сравнения, boolean-значения, ноль АКБ; момент затяжки 400 Н·м не подменяется моментом срыва 650 Н·м.
- Экспортированный XLSX независимо открыт openpyxl: 5 строк (заголовок + все 4 позиции), 8 столбцов.
- `npm run check:procurement-encoding`: строгий UTF-8 и проверка mojibake новых файлов. Миграций не было.

Артефакты локальной UI-проверки: `output/playwright/procurement-results.png`, `procurement-mobile.png`, `procurement-demo.csv`, `procurement-demo.xlsx` (игнорируются Git). Playwright работает с синтетической сессией; внешние запросы блокируются/подменяются, реальные учётные данные не используются.

Сборка имеет существующее предупреждение о размере общего bundle и смешанном импорте n8n. `npm audit` сообщает 9 уязвимостей существующих build-зависимостей (1 low, 2 moderate, 6 high); новые zod/fflate в списке не присутствуют. Массовое обновление Vite и старых зависимостей не входило в задачу.
